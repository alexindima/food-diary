# Notifications ownership inventory and extraction decision

## Verified ownership before the remaining moves

| --- | --- | --- |
| Application | `Modules/Notifications/Application`: seven command slices, five query slices, factory/mappings, feed/preferences/audience/subscription/cleanup/writer/refresh services | Preserve the existing `FoodDiary.Application.Notifications` assembly and namespaces; relocation leaves their behavior unchanged. |
| Application ports and payload contracts | All `FoodDiary.Application.Abstractions/Notifications/Common` and `Models` files | Move to module Application/Abstractions. | Persistence | Notification and subscription repositories, notification web-push enqueue adapter and processor | Move to module Infrastructure. They consume the shared context but implement exclusively Notifications-owned ports. |

## Privacy and reliability invariants

- Stored recipient linkage is UserId; subscription endpoint, P256Dh/Auth material, locale and UserAgent are private delivery metadata. Notification payload JSON may carry names/private message context. No values are copied into this report or new logs.
- VAPID private key remains configuration-bound inside the provider; public configuration exposes only enabled/public key. The adapter renders localized payloads only for the selected audience.
- Existing endpoint policy requires public HTTPS DNS host/443, rejects credentials/fragments/IP literals, disables redirects/proxies and checks resolved addresses at connection time. Preserve the network policy byte-for-byte.
- Sender limits concurrency to four, subscriptions to the existing cap, HTTP timeout to 30 seconds and overall delivery deadline to 35 seconds. External cancellation propagates; deadline expiry and per-subscription failures retain their current handling. 404/410 subscriptions are removed through the application audience capability.
- Shared outbox claiming/leases and finalization remain central. Existing policy dead-letters after ten attempts with exponential delay capped at 60 minutes and sanitized error type. This extraction does not strengthen delivery guarantees: provider partial failures are currently logged/swallowed by the sender, and crash-after-send can repeat delivery; notification ID remains the browser tag. No new deduplication, retry or rate-limit behavior is introduced.
- Notification IDs, payloads, reference-based semantic deduplication, cleanup retention, schedules, public HTTP/Swagger contracts and EF schema are compatibility invariants. Migrations/snapshot stay central.
