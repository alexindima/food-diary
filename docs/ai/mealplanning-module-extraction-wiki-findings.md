## Ownership inventory and compatibility

One physical `Modules/MealPlanning` owns two aggregate areas, MealPlans and ShoppingLists. Application keeps assembly/name `FoodDiary.Application.MealPlanning`; its two feature trees, mappings, validators, read services and `IShoppingListCreationService` boundary moved together. The 18 ports/errors/projections moved into Application/Abstractions. Central partial Errors facade forwards to owned errors for source compatibility.

Domain moves MealPlan, MealPlanDay, MealPlanMeal and MealPlanDayId. ShoppingList, ShoppingListItem, ShoppingListItemSource, their IDs/events/source enum, MealPlanId and MealPlanMealId stay central. This is a concrete CLR seam: `FoodDiary.Domain/Entities/Users/User.cs` publicly exposes `ShoppingLists` backed by `_shoppingLists`; ShoppingList exposes User; sources use plan/meal IDs. Moving Shopping into a project referencing central Domain would require central Domain to reference it back. `UserConfiguration` explicitly configures the inverse navigation's field access. Removing this public member is not compatible and was not attempted. Legacy namespaces are preserved, but moving entity assembly ownership does not promise compatibility with separately compiled binary plugins; all repository source consumers are rebuilt.

Infrastructure owns both repositories, six unchanged entity mappings and complete module DI. Model is a separate project referenced by central Infrastructure; shared FoodDiaryDbContext explicitly applies it. Historical migrations/snapshot and shared transaction context stay central. No owned jobs/provider clients were found. API and Initializer compose AddMealPlanningModule; JobManager retains its existing reference closure. No ownership of Exercises or RecipeCommunity changed.

Focused Application and Domain tests move into module projects without donor duplicates. Three self-contained methods were split out of mixed domain files; remaining cross-feature methods retain their owner. New module PostgreSQL test verifies inverse User navigation, scalar provenance without plan/recipe FK, Product SetNull and list/item/source cascades. HTTP, cross-module repository, cleanup and host tests remain central. Solution groups all five production projects and three test projects under Modules/MealPlanning, tests nested.
