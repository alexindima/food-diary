# Анализ работы вики FoodDiary

Вики уже полезна как навигация по большому репозиторию: она связывает исходники, правила, зависимости и проверки. Главные следующие шаги — исправить два подтверждённых случая ложной актуальности, сократить стоимость первого запроса и сделать оценку уверенности поиска надёжнее. Полная замена системы сейчас не обоснована.

Разбор выполнен 3 октября 2026 года в отдельном ворктри, ветка `codex/wiki-analysis`, исходный коммит `c1e5a7716abd9206d9e1dba9164f28a2c1f78e5a`. Изменения реализации вики не вносились. Временное изменение исходника для проверки графа восстановлено побайтно. Измерения и результаты сохранены в [папке доказательств](wiki-analysis-2026-10-03/manifest.json).

## Как вики работает сейчас

Система состоит из четырёх связанных частей:

1. **Навигация и правила.** `.llm-wiki/index.md` ведёт к страницам с `sources`, документации и ближайшим `AGENTS.md`. Исходный код, тесты и принятые ADR остаются авторитетными источниками.
2. **Компиляция знаний.** PowerShell генерирует JSON с проектами, символами, контрактами, frontend, данными, конфигурацией и рисками. Обновление использует зависимости между генераторами, транзакции, кеши и проверки актуальности.
3. **Поиск и планирование.** Node собирает SQLite с графом кода и полнотекстовым поиском. C# извлекается через Roslyn, TypeScript — через установленный пакет компилятора. PowerShell предоставляет `context`, `brief`, `research`, `trace`, `test-plan` и другие команды. Есть также JSON baseline для отдельных маршрутов.
4. **MCP и управление задачами.** Development MCP читает SQLite внутри процесса, кеширует результаты и выполняет составные команды через PowerShell. Отдельный набор команд хранит планы, доказательства, handoff и состояние управляемых задач.

Масштаб на исходном коммите: 120 проверяемых страниц, 317 PowerShell файлов, 367 команд в реестре. Из них 86 относятся к `core`, 80 — к `governed`, 201 — к `experimental`. JSON занимает около 11,3 MiB; самый большой индекс контрактов backend — около 4,6 MiB. Полный локальный граф содержит 9 122 файла и 33 514 поисковых документов.

Основные источники: [фасад](../../.llm-wiki/wiki.ps1), [граф](../../.llm-wiki/tools/code-graph.mjs), [конвейер индексов](../../.llm-wiki/tools/Invoke-LlmWikiIndexPipeline.ps1), [изолированное чтение](../../.llm-wiki/tools/Invoke-LlmWikiReadOnlyTool.ps1), [MCP](../../FoodDiary.Development.Mcp/Wiki/WikiQueryService.cs).

## Что показали замеры

Среда: Windows, PowerShell 7.6.5, Node 26.2.0, .NET SDK 10.0.102, TypeScript 6.0.3. Для полного графа скопирован уже установленный пакет TypeScript совпадающей версии; установка всего frontend не измерялась.

Каждую команду запускали три раза в новом процессе PowerShell. «Первый» означает отсутствие кеша результата для этого запроса; для SQLite граф уже был подготовлен. «Повторный» — среднее второго и третьего запуска. Это небольшой локальный эксперимент, поэтому из него нельзя выводить p95 рабочего использования или время CI.

| --- | ---: | ---: |

| `wiki help` | 1,36 | 0,98 |

Для поиска использовался запрос `Hydration daily water goal`, модуль Hydration, тип изменения Backend. Значения JSON и SQLite нельзя считать сравнением одинакового качества ранжирования: это разные маршруты. У тёплого JSON результат полностью берётся из кеша, поэтому меньшая задержка не доказывает преимущество JSON как поискового движка.

Первичная сборка графа backend заняла **56,61 с**, включая сборку извлекателя и SQLite reader. Добавление TypeScript к готовому графу заняло ещё **18,61 с**. Это не замер полного холодного графа одним запуском.

В первом вызове JSON через фасад создание изолированной копии заняло примерно **12,3 с**, выполнение инструмента внутри неё — примерно **27,2 с**. При повторном SQLite вызове переиспользование копии достигалось за **0,63 с**, но весь вызов занимал **3,45 с**. Остальная стоимость включает запуск процессов, Git, проверку состояния, чтение кеша и транспорт результата.

Поле `sqlDurationMs` отражает функцию поиска вместе с подготовкой кандидатов и ранжированием, а не чистое время SQL. При попадании в кеш возвращаются сохранённые тайминги с `storedTimings=true`; их нельзя выдавать за длительность текущего вызова.

Исходные данные: [27 запусков](wiki-analysis-2026-10-03/command-measurements.json), [сводка](wiki-analysis-2026-10-03/command-summary.json). Подробные локальные логи находятся в `.artifacts/wiki-analysis/`.

## Подтверждённые проблемы актуальности

### Проверка пропускает изменение уже изменённого файла

`Get-GuardState` в `Invoke-LlmWikiReadOnlyTool.ps1` сохраняет Git status и пустой словарь хешей. Если инструмент меняет содержимое файла, который уже имел статус `M`, статус до и после остаётся одинаковым. Проверка принимает вызов, а сохранённая копия остаётся испорченной.

В отдельном маленьком Git репозитории файл сначала имел `committed-content`, затем пользовательское содержимое `overlay-original`. Инструмент внутри копии записал `overlay-mutated`. Guard не отклонил вызов; следующий безопасный читатель получил `overlay-mutated`. Исходный пользовательский файл сохранил `overlay-original`.

**Последствие:** исходный checkout защищён изоляцией, но результаты следующих запросов могут основываться на испорченной копии. Это подтверждённая ошибка контроля производных данных, не наблюдавшаяся порча пользовательских исходников.

**Предлагаемое исправление:** сохранить проверку Git status для новых изменений и дополнительно сравнивать хеши уже изменённых и untracked файлов в overlay. Копию с обнаруженной мутацией удалять. Регрессия должна менять содержимое при неизменном Git status и затем проверять следующий запрос.

Доказательство: [результат](wiki-analysis-2026-10-03/dirty-snapshot-proof.json), [изолированный воспроизводитель](wiki-analysis-2026-10-03/Test-DirtySnapshotAudit.ps1).

### Сохранённые размер и время файла приводят к ложному fresh

В `build` файла `code-graph.mjs` совпадение размера и `mtime` позволяет пропустить чтение содержимого. Изменённые Git пути при этом используются для нового change-set fingerprint, но не заставляют извлечь символы заново.

Эксперимент временно заменил `Result` на `Rezult` в `Shared/FoodDiary.Results/Result.cs`, сохранив число байтов и точное время записи. Содержимое и его SHA изменились; сборка сообщила `scanned=0`, `updated=0`, а status — `changeSetFresh=true`. Старые символы остались, нового типа в графе не было. После эксперимента файл и состояние графа восстановлены.

**Предлагаемое исправление:** для изменённых Git путей проверять content hash независимо от размера и `mtime`; отдельно учесть dirty файл, который изменился повторно и остался в том же списке путей. Быструю проверку метаданных можно сохранить для остальных файлов. Строгая проверка полного содержимого должна оставаться доступной для публикации и CI.

Доказательство: [сохранённый результат](wiki-analysis-2026-10-03/preserved-timestamp-proof.json). Это крайний случай копирования или восстановления файлов, а не утверждение о каждом обычном сохранении в редакторе.

### Опубликованные индексы отстают от исходного коммита

`lint` прошёл: 120 страниц, ноль ошибок и предупреждений. Однако полный `Invoke-LlmWikiIndexPipeline.ps1 -Check` остановился на каталоге и индексе C#. Следующие этапы после неуспешной группы не выполнялись; состояние всех 12 генераторов этим запуском не подтверждено.

Диагностическая генерация в отдельные файлы показала:

- В каталоге отсутствуют ADR 0052 и ссылка из `FoodDiary.Persistence.Runtime` на `FoodDiary.Results`.
- В индексе C# записано 4 339 исходных файлов и 4 270 символов; текущая генерация даёт 4 362 файла и 4 294 символа. Есть новые типы, связанные с atomic receipts, профилем Users и доставкой сообщений.

Доказательства: [каталог](wiki-analysis-2026-10-03/catalog-drift.json), [символы](wiki-analysis-2026-10-03/symbol-drift.json). Канонические индексы при разборе не перезаписывались.

Граф может быть актуален относительно прочитанной проекции, даже если сама проекция отстаёт от кода. Следует различать **совпадение снимка**, **актуальность генерации** и **успешную проверку**. Предлагаю показывать эти три состояния отдельно в CLI, MCP и отчётах, а происхождение проекций закреплять коммитом и fingerprint входов.

Проверены семь существующих корпусов — **431 сценарий**. Их `passed` и `liveRegressionPassed` равны true. Основной 60-case корпус имеет `switchReady=false`: это другой контракт, и его нельзя скрывать под общим «всё прошло». Полная регрессия с Node/.NET parity в этот раз не запускалась.

Среди разговорных запросов таких результатов 70, из них 17 не совпадают с принятым целевым файлом. Это повод улучшить калибровку уверенности; широкая формулировка может иметь несколько разумных точек входа.

В репозитории найдено 22 корпуса с 898 сценариями; все заявленные целевые пути существуют. Уже имеющиеся и ранее использованные корпуса служат проверкой регрессий, а не новой независимой оценкой обобщения.

Предлагаю отдельно оценивать точный идентификатор, широкий запрос о поведении и выбор полезной точки входа. Для новых наборов нужны заранее просмотренные варианты релевантных ответов и разбиение по русскому языку, ролям, слоям и неоднозначности. Существующие frozen корпуса и пороги сохраняются. Нельзя повышать общий результат добавлением специальных весов для отдельных файлов.

Старая [генерируемая сводка](../../.llm-wiki/generated/context-evaluation-summary.md) помечена `stale` и датирована 28 августа. Её 99/100 и p95 266 мс не являются текущими показателями. Свежие наблюдения находятся в [quality-summary.json](wiki-analysis-2026-10-03/quality-summary.json); p95 движка в выбранных корпусах составляет примерно 322–466 мс.

## Как ускорить систему

### Сократить подготовку повседневного запроса

Это первый кандидат после исправления актуальности. Поиск движка занимает доли секунды, но фасад запускает PowerShell, Git и Node и обслуживает копию репозитория. MCP уже имеет in-process reader и кеш на 128 записей с временем жизни две минуты; это хорошая основа для повторяемых интерактивных запросов.

Предлагаемый пакет: разделить неизменяемую опубликованную проекцию и overlay рабочей копии; сделать общий read-only reader для CLI и MCP; объединять одинаковые одновременные запросы через одну выполняющуюся операцию. Существующее управление таймаутами, отменой и проверкой fingerprint сохраняется. Это архитектурное предложение, ускорение ещё не измерено.

Для нового ворктри сначала использовать доступный граф backend, когда область действительно backend. Сейчас многие planning команды выбирают JSON только из-за отсутствующего TypeScript, хотя backend-only построение уже поддерживается. Нужен маршрут по реальной области запроса и отдельная лёгкая подготовка зависимостей вики.

### Уменьшить работу при отсутствии изменений

Даже `graph build` без изменений занимает примерно 4,5 с. Он перечисляет файлы, проверяет метаданные, читает и хеширует проекции и документацию, выполняет проверки полноты. Предлагаю сначала измерить каждую стадию, затем переиспользовать проверенный manifest входов для неизменённых данных. Для dirty путей содержимое проверяется обязательно; совпадение одного `mtime` не является доказательством.

Генераторы каталога и C# перечисляют дерево через `Get-ChildItem -Recurse`, а исключают `.artifacts`, `node_modules`, `bin` и `obj` уже после обхода. Кандидат на оптимизацию — один Git-visible inventory на запуск с cached и untracked файлами, без ignored выходов. Контракт на необходимые untracked исходники надо сохранить и проверить перед заменой.

### Изменить расписание проверок по измеренным данным

Конвейер имеет зависимости между стадиями, но внутри стадии ждёт завершения всей пачки из четырёх процессов, прежде чем запускать следующую. Пул свободных workers с запуском готовых узлов графа может уменьшить хвост выполнения.

В полной проверке C# генератор занял 44,83 с рядом с тремя другими генераторами; отдельная диагностическая генерация позже заняла 12,30 с. Это сигнал проверить конкуренцию за ресурсы. Кеши и состояние машины отличались, поэтому считать разницу доказанным ускорением нельзя. Нужен контролируемый замер одинаковых входов при concurrency 1, 2 и 4, с сопоставлением полного результата.

Affected verification, receipts, resumable stages и раздельные CI shards уже реализованы. Их следует использовать и измерять. Уменьшение числа обязательных регрессий или ослабление порогов ускорением системы не считается.

## Упростить использование и поддержку

367 команд и 86 команд в core создают значительную поверхность для поддержки. Короткий help уже существует; его стоит развить в несколько понятных действий: найти код, исследовать изменение, получить план проверок, обновить индексы, проверить и передать результат. Расширенный каталог и обратная совместимость сохраняются.

В одном измеренном Assessment пакете `workflow.requiresDesign=true`, а `readiness.designCheckpoint=not-required` и `assessmentComplete=true`. Человек может понять различие, но автоматизация вынуждена выбирать, какое поле главнее. Предлагаю единственное каноническое состояние следующего действия с объяснением, а остальные поля выводить из него.

Поисковая логика дублируется в Node и C#. Перед дальнейшими изменениями полезно выделить общий контракт признаков кандидата, преобразований запросов и оценки confidence. Политика весов уже вынесена в JSON; общие синтетические проверки должны дополнять имеющуюся точную parity. Массовая перепись обоих движков в первом пакете не нужна.

| Очерёдность | Пакет | Критерий завершения |
| --- | --- | --- |
| 1 | Guard и проверка изменённых путей графа | Оба воспроизводимых случая отклоняются или корректно обновляются; пользовательские файлы сохраняются; следующие запросы читают правильные данные |

## Проверки и ограничения

Выполнены lint страниц, 27 запусков для оценки задержки, сборка backend и полного локального графа, семь поисковых измерений, проверка существования путей всех 22 корпусов, диагностика каталога и C#, два воспроизводимых эксперимента корректности. Полная проверка генераторов завершилась ошибкой актуальности исходных каталога и C#.

Обычный `wiki verify -ChangedPath docs/reports/wiki-analysis-2026-10-03.md` прошёл 7 из 7 выбранных стадий за 92,94 с. Он выбрал ноль генераторов и ноль smoke групп; этот результат не подтверждает актуальность всех индексов и не отменяет ошибку полной проверки. Для добавленных файлов отдельно проверены ссылки отчёта, кодировка, пробелы и синтаксис двух скриптов. Сохранённый изолированный воспроизводитель guard запущен повторно и подтвердил тот же дефект.

Не выполнялись полный `verify-full`, все 22 поисковых корпуса, полная .NET регрессия MCP, Node/.NET parity и измерения CI/Linux. Анализ не является успешным полным gate вики. Сохранены исходные канонические проекции, поэтому повторные замеры можно сравнить с исходным коммитом без их незаметного обновления.

## Исправления после аудита

Пакет в ветке `codex/wiki-analysis` исправляет оба воспроизводимых дефекта: guard сравнивает содержимое dirty файлов и удаляет испорченную копию; граф хеширует dirty исходники при каждом обновлении, включая повторную правку с прежними размером и временем. Регрессия графа выполняется в изолированном снимке, чтобы не менять исходники соседних проверок.

Каталог и C# используют Git-visible inventory, включающий новые неигнорируемые файлы и исключающий удалённые и ignored деревья до обхода. Конвейер заполняет освободившиеся worker слоты внутри стадии; зависимости стадий, откат и обязательные проверки сохранены. Опубликованные индексы обновлены. Проверка полного набора генераторов, полная верификация и свежесть графа имеют отдельные статусы; частичный `verify` не выставляет полный статус. Страницы с изменёнными declared sources пересмотрены, включая устаревшее описание pre-commit: сейчас он проверяет пробелы, а affected index check выполняет pre-push.

CLI и MCP используют общий C# reader ранжирования; Node сохраняет запись SQLite и диагностическое сравнение. MCP объединяет одинаковые одновременные cache misses, а отмена ожидающего клиента не отменяет владельца запроса. Backend bootstrap не требует TypeScript. Короткий help показывает повседневные действия, а research выдаёт канонический `nextActionState` без противоречивого design требования для завершённого Assessment.

Для явного запроса инструкций добавлен ограниченный отбор длинных guides по названной теме в тексте. В основном frozen наборе top-1 вырос с 57 до 58 из 60, top-10 — с 59 до 60; `switchReady=true`. Независимый unseen набор сохранил 73/100 top-1 и 94/100 top-10. Conversational сохранил 64/89 и 89/89; запросы сразу про frontend и backend теперь имеют low confidence и явную неоднозначность. Это не устраняет все неверные первые кандидаты. Контрольные запросы, ожидаемые пути и пороги не изменены. После последнего изменения reader прошли 266 focused MCP тестов, полный запуск — 416 тестов без ошибок и пропусков; дополнительно прошли 32 архитектурные проверки. Лимит параллельности передаётся всем workers полной проверки, а запись её успеха выполняется после проверки failure registry, change policy и source impact. Итоговые полные запуски сохраняются в `.artifacts/wiki-fixes` этого ворктри.

Повторные 27 запусков сохранены отдельно в `fix-command-measurements.json` и `fix-command-summary.json`; качество — в `fix-quality-summary.json`. Исходные измерения не перезаписаны. Тёплый SQLite direct составил 6,83 с, facade — 9,40 с; целевые 1,5/2 с не достигнуты. Даже пустой PowerShell вырос с 0,375 до 0,646 с, но относительный рост CLI больше. Объём dirty файлов, усиленный guard, кеши и нагрузка машины различаются, поэтому эти цифры не доказывают ни ускорение, ни величину регрессии на одинаковых входах. Снижение числа процессов и повторной работы подтверждено структурой исполнения и регрессиями, а ускорение полного CLI требует отдельного парного профилирования.
