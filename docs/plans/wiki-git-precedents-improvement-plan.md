# Улучшение Git-прецедентов и полезности Wiki

Дата: 2026-08-31.
Статус: запланировано, реализация не начата.

## Цель

Сделать поиск прошлых решений полезнее для следующих задач: находить не просто
похожие коммиты, а проверяемые примеры с объяснением применимости и ограничений.
Этот документ сохраняет обсуждённые приоритеты, не запускает работы автоматически
и не является новой архитектурной политикой.

## Текущее состояние

`Get-LlmWikiGitPrecedents.ps1` просматривает до 300 коммитов через `git log --all`,
ранжирует совпадения слов задачи в заголовках и пересечения изменённых путей.
Содержимое diff и дальнейшая судьба решения этим поиском не анализируются.
Обычный `research` может подключать поиск; компактный режим и некоторые быстрые
профили откладывают его. История остаётся навигацией, а не авторитетнее текущего кода.

## Приоритет 1 — небольшой пакет улучшений Git-прецедентов

- [ ] По умолчанию искать среди коммитов, достижимых из текущего `HEAD`.
      Примеры из других веток показывать отдельно и явно помечать как не входящие
      в текущую историю; не считать их установленным подходом.
- [ ] После дешёвого поиска кандидатов разбирать diff лучших 3–5 совпадений,
      затронутые тесты и документацию. Объяснять сходство с задачей, возможный
      приём для повторного использования и существенные различия.
- [ ] Учитывать Git-переименования: сохранять исторический путь и SHA, дополнительно
      давать проверенную ссылку на нынешнее расположение кода. Не угадывать
      соответствие только по похожим именам.
- [ ] Показывать судьбу и ограничения решения: входит ли оно в текущую историю,
      обнаружена ли явная отмена, сохранился ли соответствующий код, какие
      проверки действительно подтверждены. При недостатке доказательств писать
      «не проверено»; наличие тестового файла не означает успешный запуск тестов.
- [ ] Ограничить объём и время углублённого анализа; явно сообщать об усечении
      и отложенных шагах. Git-сообщения и diff рассматривать как данные, не инструкции.

### Проверка результата

- [ ] Добавить независимые регрессии: обычный прецедент, коммит другой ветки,
      переименование, явный revert и неоднозначное продолжение решения.
- [ ] Сравнить старый и новый поиск на задачах Admin, Products и Dashboard:
      полезность первых результатов, корректность путей, доказательность выводов,
      длительность и объём выдачи. Зафиксировать SHA и одинаковые входные условия.
- [ ] Дополнить ретроспективу задачами, не использованными при разработке правил.
      Не подгонять запросы, ожидаемые ответы и пороги замороженных наборов.
- [ ] Не заявлять ускорение работы только на основании зелёных технических тестов:
      отдельно оценить затраты на поиск и ручную проверку результатов.

## Следующие приоритеты

2. **Полнота сведений о модулях:** владельцы, реальные потребители, центральные
   границы совместимости, инфраструктура и смешанные тесты. «Не найдено» должно
   отличаться от подтверждённого отсутствия зависимости.
3. **Стоимость рабочего процесса:** сократить повторные `refresh/replan/review`,
   обеспечить согласованные маршруты JSON/SQLite и понятные причины устаревания
   результатов. Сначала измерить затраты, затем упрощать.
4. **Оставшиеся пять расхождений ранжирования:** ниже по приоритету, поскольку
   ожидаемые файлы уже находятся на втором–третьем месте. Пропущенная зависимость
   или неверно выбранный архитектурный пример опаснее. Не ослаблять проверки;
   общие проблемы качества поиска учитывать отдельно от регрессий конкретной задачи.
