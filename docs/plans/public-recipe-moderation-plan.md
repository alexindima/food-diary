# План модерации публичных рецептов FoodDiary

Первый релиз проверяет новые публичные рецепты и изменения их публичного содержимого. FoodDiary ставит проверку в PostgreSQL outbox. `omni-moderation` проверяет текст и фото, Mistral Moderation 2 проверяет выборку текстов в режиме наблюдения. В разделе «Модерация» администратор разбирает заявки и публикует версии правил. Комментарии подключаются следующим этапом через тот же контракт проверки.

## 1. Публикация рецепта и статус автора

| Действие | Что видит автор | Что видят читатели |
| --- | --- | --- |
| Сохранить личный рецепт | Сохранённый рецепт | Рецепт закрыт |
| Отправить новый рецепт на публикацию | «На модерации» и сохранённое содержимое | Рецепт закрыт до одобрения |
| Изменить публичное содержимое | «Правки на модерации» и ожидающая версия | Последнюю одобренную версию |
| Получить замечание модератора | «Требуются правки» и причина | Последнюю одобренную версию, если она есть |
| Снять рецепт с публикации | Личный рецепт | Рецепт сразу закрыт |

- `Recipes` владеет публикацией и одной активной ожидающей версией на рецепт. Каждая отправка получает новый ID версии. Фактический `Visibility` отражает доступ читателей. Для первой публикации сохраняем рецепт с фактической видимостью `Private`. Для правок опубликованного рецепта сохраняем ожидающую версию отдельно и применяем её через правила владельца при одобрении. Личные поля можно сохранять независимо. Публикация ожидающей версии сохраняет последующие изменения этих полей.
- Проводим через один сценарий создание публичного рецепта, переход из личного в публичный, изменение публичных полей, публичное копирование и административный импорт каталога. Для каталога статус импорта различает принятую на проверку заявку и опубликованный результат, повторный импорт сохраняет идемпотентность по ID каталога, а предпросмотр остаётся без записи. Импорт из ссылки или видео отдаёт черновик и попадает на проверку при отправке на публикацию. Ранее опубликованные рецепты остаются доступны и проверяются при следующем изменении публичного содержимого. [Текущие сценарии записи](../../Modules/Recipes/Application/Commands) · [Публичные страницы](../frontend/PUBLIC_RECIPES.md)
- Снимок содержит авторские публичные поля, включая название, описание, текст шагов, публичные подписи ингредиентов и фото обложки, галереи и шагов. Объём проверки сверяем с публичным DTO. Для составных рецептов и продуктов фиксируем одобренные публичные подписи, если иначе их текст может измениться вне сценария проверки. Личный `Comment` рецепта не входит в снимок. [Публичный DTO](../../Modules/Recipes/Presentation/Responses/PublicRecipeHttpResponse.cs)
- Проверяем неизменяемые файлы фото. Внешние изображения, в том числе из каталога, загружаем в управляемое хранилище с разрешённых HTTPS-источников. Загрузчик проверяет сетевой адрес при подключении и на каждом перенаправлении. Время, объём загрузки и размеры декодированного изображения ограничены. При недопустимом URL автор может загрузить файл. Новые фото ожидающей версии храним с закрытым доступом до одобрения и выдаём предпросмотр автору и модератору через авторизованный API. Ссылки обеих версий учитываем при немедленной и фоновой очистке медиа. [Безопасная загрузка источников](../../Modules/Ai/Infrastructure/Providers/Services/Recipes/RecipeSourceReader.cs) · [Хранилище изображений](../../Modules/Images/Infrastructure/AGENTS.md) · [Проверка использования фото](../../FoodDiary.ReadModel.Composition/Images/ImageAssetUsageQuery.cs)
- В пользовательском API возвращаем автору состояние публикации, ID версии и причину при запросе правок. Фоновые повторы оставляют заявку на модерации. Когда попытки исчерпаны, показываем техническую задержку и доступный способ возобновить проверку. Клиент обновляет статус по авторизованному запросу. Тексты и ошибки локализуем на русском и английском.

## 2. Outbox, провайдеры и решения

1. В транзакции сохранения Recipes фиксируем версию, действующую версию правил и задание outbox. Уникальный ключ задания включает ID проверяемой версии и вид проверки. Если сохранение откатится, задание тоже откатится. Outbox хранит ссылки на версию и медиа, без копий текста или URL доступа к фото.
2. Используем существующую инфраструктуру захвата заданий и запускаем обработчик в `FoodDiary.JobManager`. Воркер захватывает задание короткой транзакцией, вызывает провайдера после коммита и завершает обработку только при действующем захвате. Перед применением результата Recipes повторно проверяет активную версию и актуальное намерение автора опубликовать. Новая заявка, снятие с публикации и удаление отменяют применение старого результата. Одобрение, отклонение и переход в ручную очередь сохраняются атомарно с итогом обработки и повторяемы без второй публикации. [Механизм outbox](../../Shared/FoodDiary.Outbox.Infrastructure/Persistence/OutboxProcessingEngine.cs) · [Фоновые задачи AI](../backend/AI_RECOGNITION_JOBS.md)
3. Общий контракт проверки принимает версию материала, части текста и ссылки на конкретные фото. Адаптеры объявляют поддерживаемые типы входа и категории. В результате храним ID запроса провайдера, идентификатор модели, её исходные флаги и баллы, тип входа, привязку к полю или фото и решение по правилам. Предлагаем разместить обработку проверок, правила и очередь в `ContentReports`, а HTTP-адаптеры в его `Infrastructure`. `Recipes` применяет решение через свой контракт. `Admin` вызывает контракты владельцев, `JobManager` запускает обработку. Направление зависимостей проверяем архитектурными тестами. [Границы модулей](../BACKEND_MODULE_MAP.md)
4. Основной адаптер вызывает `/v1/moderations` OpenAI для текста и фото. Для первого релиза используем флаги поддерживаемых категорий. Все обязательные проверки успешно пройдены → публикуем. Значимый флаг → ручной разбор. Временная ошибка или неполный ответ → ожидание повторной попытки. Привязку к конкретному фото сохраняем на уровне отдельной проверки. Пороги по баллам добавляем только после калибровки для конкретной модели, категории и типа материала. [Результаты OpenAI](https://developers.openai.com/api/docs/guides/moderation#understand-moderation-results)
5. Для детерминированной выборки версий запускаем отдельные задания Mistral `mistral-moderation-2603` по тексту с собственной очередью исполнения и ограничением параллелизма. Результат доступен в админке и аналитике. Время ответа, ошибка или несогласие Mistral не влияют на основную проверку, очередь ручного разбора или публикацию. Сопоставляем документированные категории отдельно по моделям. При пилоте модератор проверяет образцы с расхождениями и часть выборки, где обе модели пропустили текст. [Модель Mistral](https://docs.mistral.ai/models/mistral-moderation-26-03) · [Особенности идентификатора модели](https://docs.mistral.ai/studio/safety-moderation/quickstarts/moderate-an-input)
6. У каждого провайдера свой лимит параллелизма и общий бюджет на все экземпляры воркера. Читаем реальные лимиты проектов. При временном `429` учитываем `Retry-After`, при временных сбоях применяем отложенные повторы с ограничением числа попыток. Ошибки доступа, конфигурации и исчерпанный бюджет помечаем отдельно и показываем оператору. После исчерпания повторов заявку можно возобновить из админки. [Лимиты OpenAI](https://developers.openai.com/api/docs/models/omni-moderation-latest#rate-limits) · [Повторы OpenAI](https://developers.openai.com/api/docs/guides/rate-limits#retrying-with-exponential-backoff) · [Лимиты Mistral](https://docs.mistral.ai/admin/billing-usage/usage-limits)

## 3. Очередь и правила в админке

- В разделе «Модерация» добавить «Автопроверки» и «Правила». Очередь фильтруется по статусу, категории и периоду. В карточке показываем именно проверенную версию, поле или фото, сигналы моделей, сработавшее правило, историю попыток и решений. Просмотр ожидающего содержимого требует административного доступа и исключает публичное кэширование. Существующие жалобы обрабатываются через свой сценарий. [Текущий API модерации](../../Modules/Admin/Presentation/Controllers/AdminModerationController.cs)
- Действия очереди включают одобрение, запрос правок с причиной и повторную проверку после исчерпания попыток. Для решения проверяем ожидаемый ID версии и состояние заявки, при конфликте возвращаем `409` и обновляем карточку. Храним автора решения, время и причину. Серверная авторизация защищает чтение и каждое действие.
- В правилах отдельно настраиваем текст рецепта и фото. Доступные параметры включают категории для ручного разбора, долю наблюдения Mistral и выбор из поддерживаемых провайдеров и версий моделей. В первом релизе OpenAI остаётся основной проверкой, Mistral можно включить для наблюдения за текстом. Резервную проверку и второе мнение с влиянием на публикацию рассматриваем после пилота. Публикация правил требует валидного набора обязательных проверок. Ключи провайдеров остаются в серверной конфигурации.
- Сохраняем черновик, валидируем его, публикуем неизменяемую версию и записываем автора, время и изменения. Новые заявки получают действующую версию. Откат правил создаёт новую версию с прежними настройками. Повтор технической ошибки использует исходные правила. В карточке видно, по каким правилам было принято решение. [Пример версий и истории в админке](../../Modules/Admin/Presentation/Controllers/AdminAiPromptsController.cs)
- В статистике считаем уникальные версии рецептов за период, долю отмеченных и результаты ручного разбора. Текущий размер очереди, возраст старейшей заявки, повторы, `429`, задержки и ошибки показываем отдельно. Mistral получает собственные показатели охвата и расхождений по сопоставимым категориям.

## 4. Данные, проверки и включение

- Передаём провайдерам только явно отправленные на публикацию поля и изображения без метаданных. Для Mistral до подключения пользовательской выборки проверяем доступ к API, настройки хранения и использования данных, бюджет и назначение обработки. Описываем передачу при публикации. Для ожидающих версий, проверок и аудита задаём срок хранения. Удаление аккаунта очищает ожидающие материалы, ссылки на медиа и связанные с пользователем записи, в том числе когда FoodDiary сохраняет обезличенный публичный рецепт. Логи содержат ID и итог обработки без текста, фото, ключей и подписанных ссылок. [Жизненный цикл данных FoodDiary](../backend/PERSONAL_DATA_LIFECYCLE.md) · [Данные OpenAI](https://developers.openai.com/api/docs/guides/your-data#storage-requirements-and-retention-controls-per-endpoint) · [Данные Mistral](https://docs.mistral.ai/admin/monitor-comply/zero-data-retention)
- Проверяем PostgreSQL-сценарии сохранения заявки и отката транзакции, параллельного захвата, повторной доставки, позднего ответа после правки, снятия с публикации или удаления, а также сохранения медиа обеих версий. Проверяем все пути записи с публичной видимостью, анонимную карточку, каталог, SSR и sitemap. Недопустимый URL или перенаправление на закрытый сетевой адрес отклоняется. Прямой доступ к ожидающим фото без авторизации закрыт. Личное сохранение не создаёт заданий. Старые публичные ссылки продолжают открываться на одобренной версии.
- Тесты провайдеров используют контролируемые ответы для чистого результата, флага, неподдерживаемой категории, неполного ответа, таймаута, `429` и исчерпания попыток. Проверяем, что отключение Mistral не влияет на основное решение. Тесты API и UI покрывают доступ автора и администратора, конфликт ручного решения, настройки правил и русские и английские статусы. При изменении HTTP обновляем snapshots и генерируем SDK клиента и админки. [Стратегия тестирования](../TESTING_STRATEGY.md) · [Правила клиентского проекта](../../FoodDiary.Web.Client/AGENTS.md)
- Сначала реализуем схему, версию публикации и outbox. Затем адаптер OpenAI и обработчик в JobManager, пользовательские статусы, очередь админки и версии правил. После выкладки всех совместимых экземпляров API и воркера прогоняем сценарии на тестовых данных, затем включаем обязательную проверку версий, отправляемых на публикацию. Начинаем наблюдение Mistral с ограниченной выборки и сравниваем с ручными оценками на русском и английском. При остановке обработки новые версии ожидают проверки, а уже одобренные остаются доступны. Работу над реализацией ведём в отдельном контексте Wiki для межмодульной задачи. [Процесс изменения](../ai/AI_WORKFLOW.md)

## 5. Комментарии после запуска рецептов

`RecipeCommunity` подключает создание и редактирование комментариев к общим outbox, правилам и очереди. Модуль хранит версию текста и применяет решение сам. Автор видит ожидающий текст, читатели видят только одобренный. Уведомление о новом комментарии уходит после первой успешной публикации. Перед подключением интерфейса проверяем существующий API, пользовательские жалобы и ограничения частоты публикаций. [Текущий API комментариев](../../Modules/RecipeCommunity/Presentation/RecipeComments/Controllers/RecipeCommentsController.cs) · [Создание и уведомление](../../Modules/RecipeCommunity/Application/RecipeComments/Commands/CreateRecipeComment/CreateRecipeCommentCommandHandler.cs)
